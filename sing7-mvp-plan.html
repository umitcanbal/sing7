SING7 — MVP Technical Plan

A music app that shows lyrics with chords above the words, auto-scrolls at the player's pace, and lets people play along comfortably. The song library is a Git repository of plain-text files; a Go server reads, parses, and serves them from memory.

Frontend: Next.js Backend: Go Song source: akordy Git repo (.txt) Storage: in-memory Runtime: Docker

1. Input: the song repo

There is no upload or paste flow. The song library is a Git repository (akordy) of .txt files, one file per song. Adding a song means adding a file and committing it. The Go server reads the folder and serves what it finds.

akordy repo (.txt) → Go reads folder → parse per format spec → in-memory index → REST → Next.js
The repo
akordy/
  Coldplay - Don't Panic.txt
  Blink-182 - I Miss You.txt
  Radiohead - Creep.txt
  Ready Kirken - Zejtra mám.txt
  ... (28 songs today, ~388 KB total)
  .cursor/skills/strumming/SKILL.md   ← the format spec
  scripts/                            ← normalize + validate helpers
Consistency is the whole bet. This approach works because the files follow one documented convention. There is no CI on the akordy repo, so consistency is kept by a validator run at server load (and optionally by hand when editing) — a malformed file is skipped rather than reaching the app (see §6).

2. Anatomy of a song file — terminology

This section fixes the vocabulary. Every named element below actually appears in the .txt files; from here on, these words mean exactly what is shown. A file has two zones: a body (what a player reads) and a metadata footer (facts about the song). Not every element is in every file — the “In how many” figures are counts across the 28 songs in the repo today.

2.2 Strum pattern — tag B, in 9 / 28

Two stacked rows: strokes on top, beats below, one glyph per slot, equal slot counts. A file may carry several, each with a label saying where it's used — your example has Intro / verse and Pre-chorus / chorus; others label a main pattern plus an extended outro one.

A strum pattern (Blink-182, “Intro / verse”)
Intro / verse       ← label (free text: a section name, or "Strumming (122 BPM)")
↓ · ↓ · ↓ ↑ ↑ ↓     ← strokes row  (what the strumming hand does)
1 & 2 & 3 & 4 &     ← beats row    (the count each slot lands on)
GlyphMeaning
↓ / ↑Down / up stroke.
▼ / ▲Accented (harder) down / up stroke.
x / XMuted (percussive) strum.
·Rest — no strum on that slot; let the chord ring.

The beats row uses counts and & (the “and” between beats). Slot counts seen: 4, 5, 8, and 12. In the MVP we display the grid; we don't sequence audio from it.

2.3 Chord shape definition — tag C, in 19 / 28

One chord per line: the name, a colon, then one number per string, read low string → high string (guitar: E A D G B e). It is literally where the fingers go, which is exactly what the diagram draws.

Reading one definition
C/B:  x 2 3 0 1 0
       │ │ │ │ │ └ high e string, open (0)
       │ │ │ │ └── B string, 1st fret
       │ │ │ └──── G string, open
       │ │ └────── D string, 3rd fret
       │ └──────── A string, 2nd fret   ← the B in the bass ("/B")
       └────────── low E string, muted (x = don't play)
TokenMeaning
xMuted — don't sound that string (parsed as -1).
0Open string — played, no finger.
1, 2, …Press that fret.
(or x33201)An alternate voicing the player may substitute (seen in 2 files).

The chord name encodes theory the app mostly passes through: slash chords (C/B = a C chord with B in the bass), extensions (Cadd9, Fmaj7), and altered tones (Fadd#11).

Shapes vs. how they sound. In your example the shapes are ordinary C-shapes, but the metadata says Capo 2nd fret / Key B — so those C-shapes actually sound in B. The shape tells you what to finger; the metadata tells you how it sounds. They are separate on purpose.
See other variations of (C) — chord shape definition

The line shape barely varies: Name: then exactly six single-character fret tokens (x or one digit), low→high. Verified across the repo — all 88 definitions have 6 tokens and no fret is ever two digits. The chord name before the colon can be as fancy as it likes (Fmaj9, A/C#, Fadd#11): that's content in the name slot, not a shape difference — Fmaj9: 1 3 3 0 1 x parses exactly like C: x 3 2 0 1 0.

The one genuine deviation is a trailing free-text alternate voicing, in two flavors:

VariationReal example
Compact fret-string alternateFadd#11: 1 3 3 2 0 1 (or x33201)
Prose alternate instead of fretsD/F#: 2 x 0 2 3 x (or thumb on 2nd fret E)

Parse rule: after the six tokens, anything in ( … ) is a human note — keep it, don't read it as frets. (Only 2 files carry such a note.)

2.4 Section tag — tag D, in 15 / 28

A bracketed label that starts a part of the song. About half the files have none and are one continuous run instead.

Observed section tags
English:  [Intro] [Verse 1] [Pre-Chorus] [Chorus] [Bridge] [Interlude] [Outro]
Variants: [Chorus A] [Chorus B]   (letters)   [Ref. 2x] [Chorus 5x]  (repeat counts)
Czech:    [Sloka 1] [Ref.] [Mezihra]
Sections are optional. 13 of 28 songs have no tags — they are one continuous run of chords over lyrics. A song with no tags is treated as a single unlabelled section. Don't build core features that require named segments; treat “jump to chorus” as an enhancement for songs that happen to be tagged.
See other variations of (D) — section tag

There's essentially no shape variation: the tag is always [label], and for the MVP the whole bracket content is the display label, shown verbatim (13 of 28 files have no tag at all). The label text is free-form — which only matters if a later feature tries to group or navigate sections:

  • Free-form & bilingual — English [Chorus] [Pre-Chorus] [Interlude], Czech [Sloka 1] [Ref.] [Mezihra]; numbering [Verse 1] and lettering [Chorus A] are just more label text. The parser can't assume English.
  • Repeat counts like [Chorus 4x] or [Ref. 2x] mean “play it N times.” The MVP has nothing that repeats sections, so [Chorus 4x] and [Chorus] parse identically — the 4x is just part of the heading. Only a future “jump to / group sections” feature would ever want to strip the Nx to normalise labels.

2.5 Chord line & lyric line — tags G + F, in 28 / 28

The one thing every file has. A chord line (only chord names) sits directly above a lyric line, and the core rule is: a chord's first character sits in the column where the change is heard. Files are monospace so the columns line up.

Alignment (columns matter)
Am              C
Bones, sinking like stones
        Fmaj7
All that we fought for

Am starts at column 0 (over “Bones”), C at the column over “like”. The parser reads those columns to attach each chord to the right piece of text.

See other variations of (F) — lyric line

Structurally the plainest element — free UTF-8 text (English, Czech, Italian), with punctuation that belongs to the words. Only one point is parse-relevant:

  • A lyric line may have no chord line above it — the previous chord is still held, so not every lyric row has a partner chord row.

Rule of thumb: any body line that isn't a tag, chord line, definition, strum, or fence is lyric text.

See other variations of (G) — chord line

There's really one distinction the parser must make, and it's structural:

  • Chord line (G) vs. chords-only line (E) — the same-looking row of chord names is a chord line when a lyric sits directly under it, and a chords-only line when nothing does.

The chord tokens use the same names as the definitions (C/B, Cadd9, Fadd#11) and are placed by column — that's content and alignment, not a shape variation. Attachment happens at each chord's first character (see §4, Step 4).

2.6 Chords-only line — tag E

A chord line with no lyric under it — an intro, interlude, or instrumental run. Two written forms, and it often carries a repeat hint in parentheses.

Both forms, with margin annotations
C   C/B   Am   C/B                    ← bare form
| Am | C | Fmaj7 | Fmaj7 |   (×2)      ← pipe form (3 files)
| C | C | Am | F G |   (riff ×2)       ← annotation = a repeat/how-to hint

Margin annotations like (×2), (×4 takty) (“bars”), or (riff ×2) appear in 12 of 28 files. They are shown as-is next to the row.

See other variations of (E) — chords-only line

Two genuinely different line shapes:

Either shape may carry a trailing free-text hint in parentheses — a count (×2), a bar count (×4 takty), or a whole sentence (riff ×2½ a fade out). Shown as-is; not parsed.

See other variations of (H) — footer fence

The most uniform element in the whole corpus: no variation observed. Every one of the 28 files uses a run of ─ (U+2500), about 40 characters wide, exactly twice — one line opening the footer and one closing it.

For the validator: match a run of ─ only — plain ASCII -, = and _ are never used as fences here — and expect exactly two per file.

3. Parsed data model

The parser turns each file into one song object held in memory. Chord placement uses ordered parts ({ chord, text }); the object also carries the strum, chord shapes, and metadata the format provides.

This model is a first draft, not a fixed contract. It's a reasonable starting shape, but it should be refined during parser development whenever real song files reveal a more natural representation. The parser and the corpus shape the model — the model should not constrain them. (The public API is insulated from this churn by a separate response type; see §7.)

4. How the Go parser works

Parsing runs once per file when the server reads the repo. It is a small state machine over the lines.

Step 1 — Split body from footer at the ──── fence
body   = everything above the first ──── fence
footer = the Label/value pairs between the fences
Step 2 — Read the footer into fields (with the label map)
Key  → meta.key = "F"      Tempo → meta.tempo = "122 BPM"
Time → meta.time = "4/4"   Capo  → meta.capo = 0   ("none" → 0)
Artist/Autoři "… (2000)" → meta.year = 2000   (trailing (YYYY); optional, 10/28)
unknown label → append to meta.notes[]
Step 3 — Walk the body, classifying each line
Each line is matched against a fixed, ORDERED list of line-types; the first
rule that matches wins. A line that matches nothing is NOT assumed to be a
lyric — it is handed to the validator as unrecognised.

  [Section]                       → section tag      (D)
  Name: x 3 2 0 1 0               → chord definition  (C)  → file shape override
  ↓ ↑ ▼ · x  row                  → strum strokes     (B)
  1 & 2 & 3 & 4 &                 → strum beats       (B)
  e|-0-  B|-0- … (6 string rows)  → TAB block              → recognised, skipped
  every token is a valid chord    → chord row         (E/G)
  has real word text              → lyric             (F)
  none of the above               → UNRECOGNISED → validator, never a lyric

  (no [Section] seen yet → open one implicit section, label = null)

Then a second pass pairs each chord row with the line beneath it:
  chord row + lyric under it   → chord line (G)  → build parts (Step 4)
  chord row, nothing under it  → chordsOnly line (E)
  lyric with no chord above it → held-chord line (F, allowed — see §2.5)
Lyric is a positive match, not a fallback. A “chord row” requires every whitespace token to match the chord grammar (root A–G, optional accidental, quality, extension, optional /bass) or a | bar; a “lyric” requires actual word text. Anything that is neither a recognised structural type (tag, fence, definition, strum, TAB) nor plausible lyric text is surfaced by the validator instead of being swallowed into the song — which is exactly how the All Time Low TAB block gets caught rather than rendered as words.
Step 4 — Turn a chord line + lyric line into parts
chord line:  "Am              C"      columns: Am@0, C@16
lyric line:  "Bones, sinking like stones"

split the lyric at each chord column (snap to the nearest
word gap when a column lands mid-word):

Part 1: chord = "Am", text = "Bones, sinking "
Part 2: chord = "C",  text = "like stones"
Snapping is a judgment call. Real chord sheets occasionally place a chord column mid-word. The parser needs one clear rule (e.g. snap to the preceding space); the files remain the source of truth, and the validator flags anything ambiguous so a human fixes the file rather than the parser guessing.

5. Chords: diagrams & transpose

Two things the app does with chords: draw them (diagrams, §5.1–5.2) and shift them (transpose, §5.3). Both interpret the chord name as a small domain object.

Diagrams are drawn by a React SVG renderer from finger data. The data is assembled per song by merging a shared base dictionary with the file's own definitions.

5.1 Where a shape comes from

SourceHoldsWins when
Base dictionary (in the backend, once)Common open/barre shapes: C, G, Am, D, E, F, Em…Used when the file does not define the chord.
File definitions (in the .txt)Song-specific voicings: Fadd#11, C/B, G/B, capo shapes.Always override the base for that song.
Neither has it—Show the chord name without a diagram; add it to a missing-diagram report.
Merge rule: file definition wins → else base dictionary → else no diagram. This keeps files small (they only define the unusual chords), lets shape-less songs still render, and removes the risk of the same common chord being duplicated inconsistently across files.

5.2 From text to shape

Chord definition in the file → parsed shape
C:  x 3 2 0 1 0     →     { "name": "C", "frets": [-1, 3, 2, 0, 1, 0] }

x becomes -1 (muted string). Six values means a six-string guitar shape. The renderer draws one vertical line per value, so it stays instrument-agnostic and a future four-value ukulele shape would just work.

base dictionary + file defs → merged chordShapes → embedded in the song JSON → React SVG renderer → popup diagram

5.3 Transpose — chord-name domain utility

Transpose shifts every chord up or down by a number of semitones. It works purely on chord names — independent of diagrams and of the UI — so it belongs in a small, reusable, unit-tested module (its own build task), not scattered through frontend code.

Chord-name model (root · suffix · optional bass)
Cadd9   → root "C"   suffix "add9"  bass —
F#m7    → root "F#"  suffix "m7"    bass —
C/B     → root "C"   suffix ""      bass "B"
A/C#    → root "A"   suffix ""      bass "C#"

Algorithm: parse the name → map the root (and bass, if present) to a pitch class 0–11 → add the offset (mod 12) → re-spell → reattach the untouched suffix. Only root and bass move; the suffix (m, maj7, sus4, add9…) is carried through verbatim.

Enharmonic spelling policy (a real decision). A shifted pitch can be written two ways (A# vs B♭). MVP policy: if meta.key is known, spell to match that key's accidentals; otherwise default to sharps. This keeps output predictable and testable. Capo is separate — it changes sounding pitch, not the written chord names — so transpose and the capo hint stay independent.

Because it's a pure function of (chord name, offset), it is trivially unit-testable and reusable by any surface. Where it runs — precompute on the server or shift live in the client — is an implementation choice; the logic lives in one shared utility either way.

6. Validation

A validator checks a .txt file against the format rules before it is trusted. It is separate from the parser: the parser turns a file into data; the validator confirms the file is well-formed first.

When the server loads (primary — the only enforced guardrail)

On startup the parser reads every file and validates it first. A malformed file is logged and skipped, not half-parsed or crash-inducing, so one bad file never takes down the library. There is no CI on the akordy repo (and none is planned), so this load-time check is the only guarantee the running app actually has.

When songs are edited (optional convenience)

The same validator can be run by hand (or wired as a local pre-commit hook) against the files being edited, to catch format drift before committing. It's a convenience for whoever curates the songs — not an enforced gate, since nothing runs it automatically.

Same validator, two moments: it is not re-run against unchanged files on a schedule — it fires at server load (always), and optionally when an editor chooses to run it.

B4Hard tab elsewhere in the body (a lyric line with no chord above it) — sloppy but harmless to alignment.Warning
B5A line in the lyric bucket that looks structural (contains |…-…| bars, is mostly digits/dashes, or starts with a string name + |) — guards tags E / F / G.Report
B6Guitar-TAB staff block (six consecutive e|… B|… G|… D|… A|… E|… lines): recognised, kept verbatim, not parsed as lyrics or chords. 1 file today.Report
F1FooterEvery non-blank footer line is label + whitespace + value.Error
F2Unknown footer labels — allowed, kept as notes, but surfaced so the label map can grow deliberately.Report
F3Chords used in the body but resolvable to no shape (neither file definition nor base dictionary) — the missing-diagram list.Report

Deliberately not a rule: section tags are not required — a song with none is valid and parsed as one implicit section (label = null). Column alignment that lands a chord mid-word is not rejected either; the parser's snap rule (§4) handles it, and B5 only flags lines that look structurally wrong.

6.2 Dev-time validation CLI

Since nothing validates songs automatically, we ship a small command-line tool so a developer or song curator can check files locally, before committing. It's the "optional convenience" run from §6 — fast feedback that stops a malformed file from silently vanishing at load time.

One rule set, two entry points. The CLI is a thin wrapper over the same validator package the server runs at load time — it must not reimplement the rules. Shared code means the check a developer runs locally is byte-for-byte the check the server applies, so the two can never drift apart.
Usage
song-validate path/to/Song.txt ...   # check specific files
song-validate --all                  # scan every .txt in the song folder

# output: one line per problem, grouped by file
Radiohead - Creep.txt: OK
Some Song.txt: ERROR line 12: two chord lines in a row
Some Song.txt: WARN  line 40: line looks like TAB, not lyrics

exit code 0 = all valid · non-zero = at least one ERROR (warnings don't fail)
  • Same severities as §6.1 — an Error fails the run (non-zero exit); a Warning is reported but passes.
  • Opt-in, not enforced — a developer may wire it as a local pre-commit hook, but nothing forces it to run. It stays a convenience, consistent with "no CI."
  • Read-only — it only reports; it never rewrites song files.

7. API contract

The data is read-only, so the API is read-only REST. There is no import endpoint. The server serves from its in-memory index.

The API response is a separate type from the internal model. The parser's internal Song struct (§3) is not serialized directly. A dedicated response DTO is mapped from it before returning JSON. This makes the REST payload an explicit, stable contract, lets the internal model evolve freely as parsing matures (§3), and keeps implementation details private. At first the DTO may look almost identical to Song — that's fine; the value is the seam, not the shape. The JSON shown below is the DTO.

8. Architecture

8.1 The server

Go service, in-memory index. On startup it walks the akordy folder, parses every .txt file, merges chord shapes, and builds a map[slug]Song plus a small search list. All requests are served from RAM. At 28 songs / 388 KB — or even thousands of songs — this stays in low single-digit megabytes.
Startup
load base chord dictionary
read akordy/*.txt
  → validate + parse each file  → Song
  → merge base + file chord shapes
  → index[slug] = Song
  → build search list (title, artist)
serve REST from the index

8.2 Getting the files to the server

Option A: bake into the image

Docker build
COPY akordy/ /app/songs/
# server reads /app/songs on boot

Simple and reproducible. A new song ships as a new image build. Good for the MVP.

Option B: clone/pull at runtime

Boot or webhook
git clone akordy → /app/songs
# POST /api/reload after a git pull

Add songs without rebuilding. Slightly more moving parts (repo access, reload trigger).

Suggested MVP choice: Option A (bake the repo into the image). Add /api/reload + Option B later if editors want faster turnaround.

8.3 Repository strategy

Monorepo
repo/
  frontend/     # Next.js
  backend/      # Go server + parser + base chord dictionary
  akordy/       # the song files (or a Git submodule)
  docker-compose.yml

The akordy repo can stay separate and come in as a submodule, keeping song editing independent from app code. Either way, the validator runs at server load on the song files (there is no CI).

8.4 Deployment

Suggested MVP choice: one server, two containers (Next.js + Go). No database container. Frontend and backend still deploy independently.

A1 — Why a song file stores chord shapes

Question that prompted it: a chord like “C” is universal and shared across songs, so why store its shape (C: x 3 2 0 1 0) inside a song file at all?

Assumption: a single chord name maps to many valid shapes (voicings) — e.g. open C, barre C at the 3rd fret, C at the 8th fret. A base dictionary can only pick one default. The shape written in a .txt file is therefore the arranger's chosen voicing for that specific song (matching the recording / neighbouring chords), not a coverage mechanism. So: the base dictionary supplies a default per chord name, and a file definition overrides only to select a particular voicing.

What it decides: whether file chord definitions are treated as per-song overrides (our current design) vs. redundant duplicates we could ignore. If the assumption is wrong, the merge rule in §5 changes.

Owner: Business/content (people sourcing the tabs) + Technical.

Status: 🟢 Confirmed — signed off 2026-07-20. File chord definitions are per-song voicing overrides; the §5 merge rule (file → base → none) stands.

Known limit to check: a file gives one chosen voicing per chord, not a ranked list of alternatives. “Show me other ways to play this C” would come from the dictionary, not the file — confirm that's acceptable for the MVP.
