SING7 — Build Steps

An actionable, ordered build plan for the SING7 MVP. Split into two phases: Phase 1 gets a real, usable app running end-to-end; Phase 2 adds the nice-to-haves once it works.

Sequencing principle: get a working app first — browse songs, open a song page, see chords over lyrics, auto-scroll. Anything not needed for that (chord diagrams, transpose) is Phase 2. There is no separate validator: the parser is the only guardrail — it returns an error on malformed input and the store skips those files.
How to read each step: Goal = one sentence, the point of the step · Implementation tasks = the concrete checklist · Done when… = acceptance criteria (tick every box before moving on) · Result = the new capability you have.

Phase 1 — get a working app

  1. Walking skeleton — a server that runs START HERE

    GoalStand up a runnable Go project with an HTTP server you can curl, before any real logic exists.
    Implementation tasks
    1. Run go mod init sing7 (or your module path).
    2. Create the folder layout: cmd/server/main.go, plus empty packages you’ll fill later — internal/song, internal/parser, internal/store, internal/httpapi.
    3. In main.go, start a net/http server on a configurable port (e.g. :8080).
    4. Add GET /api/songs returning hardcoded JSON {"songs":[]}.
    5. Add GET /health returning 200 OK.
    6. Run it: go run ./cmd/server and curl both endpoints.
    Done when…
    • go run ./cmd/server starts with no error.
    • curl localhost:8080/api/songs returns {"songs":[]}.
    • curl localhost:8080/health returns 200.
    Result / new capabilityYou have a running server and a project skeleton. Every later step now has a real place to live, and you can see changes run immediately.

  2. Confirm assumption A1 DONE

    A decision gate, not a coding task — included for completeness because it unblocks the chord-diagram work in Phase 2.

    GoalDecide whether file chord definitions are per-song voicing overrides or redundant duplicates — it determines the chord-shape merge rule.
    Resolution ✅ (2026-07-20)They are per-song voicing overrides. The merge rule is fixed: file → base → none.
    Result / new capabilityNo design decision blocks the chord-shape work. The Phase 2 diagram step can be built exactly as specified; nothing else is waiting on a decision.

  3. Define the Song data model (the shared contract)

    GoalDefine the internal Go Song type that the parser produces, the store holds, and the DTO maps from — the spine everything else imports.
    Implementation tasks
    1. Create the song package (internal/song/song.go).
    2. Define the structs from §3:
      • Song{ Slug, Title, Artist, Meta, Strum, ChordShapes, Sections }
      • Meta{ Key, Capo, Time, Tempo, Year, Notes }
      • Strum{ Label, Strokes, Beats }
      • ChordShape{ Frets []int, Source string }, held in map[string]ChordShape
      • Section{ Label *string, Lines []Line } — Label == nil means untagged
      • Line{ ChordsOnly bool, Parts []Part }, Part{ Chord, Text string }
    3. Fix the zero-value conventions: Label *string for null, Capo defaults to 0, muted string = -1 in Frets.
    4. Add a slug helper (title + artist → kebab-case).
    5. Keep the package dependency-free — it must import none of your other packages.
    Done when…
    • go build ./internal/song compiles standalone.
    • A tiny test can construct the §3 worked example (Don’t Panic) literally from the structs.
    • Nothing in the package imports parser, store, or http.
    Result / new capabilityYou have the shared contract. Every downstream package can now be written against a concrete type instead of a sketch. Per §7 this internal model is never serialized directly — a separate DTO (Step 5) maps from it, so it can evolve freely.

  4. Build and prove the parser HIGHEST RISK

    GoalBuild a standalone parser that converts a song .txt file into the internal Song model — and rejects malformed files with an error.
    Implementation tasks
    1. Create the parser package.
    2. Implement the parsing pipeline (§4):
      • parse title and artist
      • parse metadata / footer
      • classify every line (ordered rules; lyric is a positive match, not a fallback)
      • build sections (no tag → one implicit section, label = null)
      • detect chord lines, lyric lines, chords-only lines
      • parse chord definitions
      • parse strumming blocks
      • detect & skip TAB blocks (don’t parse as chords/lyrics)
      • pair chord lines with lyric lines (column-snap rule for attachment)
      • build the final Song
    3. Fold the necessary format checks in here (title line, two fences, line-type recognition, etc.) and return an error when a file breaks them — this is the app’s only guardrail, so it lives in the parser, not a separate validator.
    4. Write focused unit tests for the trickiest parsing rules.
    5. Choose several representative songs and write detailed assertions on the parsed output.
    6. Add a corpus test that parses all 28 songs. Use §6.3 as the map: known-tricky files (Lucie - Medvídek.txt irregular fence, trailing-note files) plus the listed clean reference files.
    7. Run the complete suite: go test ./...
    8. Fix parsing issues until all tests pass.
    Done when…
    • Every song parses successfully.
    • Representative songs produce the expected Song structure.
    • The parser returns errors for malformed input instead of silently producing incorrect output.
    • All parser tests pass.
    Result / new capabilityA standalone parser callable directly from Go — song, err := parser.Parse(data) — that returns a populated Song (or an error) for a given .txt file. Fully tested and independent of the HTTP server, store, and frontend. It is also the guardrail: bad files error out here and get skipped by the store.
    Highest risk in the whole plan — find format surprises here, on day one, not through the server.

  5. In-memory store (the “database”)

    GoalOn startup, turn the akordy folder into a queryable in-memory index of songs.
    Implementation tasks
    1. Create a store package holding map[slug]Song + a search list (title/artist).
    2. Implement Load(dir): walk *.txt; for each file — parser.Parse → on error, log and skip; else insert.
    3. Build the search index (lowercased title + artist) for ?q=.
    4. Expose All(), Get(slug), Search(q).
    5. Log a load summary: N loaded, M skipped (with reasons).
    6. Test Load against the real akordy folder: expected count loaded, known-bad files handled.
    Done when…
    • Loading the real folder indexes the expected number of songs; bad files are skipped with a logged reason (no crash).
    • Get(slug) returns a full song; Search("panic") finds Don’t Panic.
    • Startup prints a clear load summary.
    Result / new capabilityThe app’s “database.” The whole library is queryable in memory by slug and by search term — ready for the API to serve.

  6. Read-only REST endpoints + response DTO

    GoalServe the in-memory store over HTTP through a stable DTO, replacing the Step 0 stub.
    Implementation tasks
    1. Define response DTOs in httpapi (SongDTO, SongListItemDTO) — separate types from Song.
    2. Write mappers toSongDTO(Song) / toListItemDTO(Song).
    3. Implement handlers backed by the store:
      • GET /api/songs?q= → list/search (list-item DTOs)
      • GET /api/songs/{slug} → one full song DTO (404 if missing)
      • POST /api/reload (optional) → re-run store Load
    4. Replace the Step 0 hardcoded handler with the real one.
    5. Set JSON content-type; handle not-found and the query param.
    6. Test handlers with httptest: known slug → 200, unknown → 404, ?q= filters.
    Done when…
    • curl /api/songs returns the real library; ?q=panic filters it.
    • curl /api/songs/coldplay-dont-panic returns the full parsed song as a DTO.
    • Unknown slug → 404. The internal Song is never serialized directly.
    Result / new capabilityThe backend is feature-complete for the MVP: a real, queryable, read-only song API over HTTP. The frontend can now be built against a live contract.

  7. Frontend — the core player experience

    GoalBuild the Next.js UI that lets a player find a song, open it, read chords over lyrics, and auto-scroll — the usable MVP.
    Implementation tasks (in dependency order)
    1. Scaffold the Next.js app; wire an API client to the Go backend.
    2. Browse/search page (consumes GET /api/songs?q=).
    3. Individual song page (route by slug; consumes GET /api/songs/{slug}).
    4. Render sections → lines → parts as chords-over-lyrics.
    5. Auto-scroll: hands-free scroll at a user-controlled speed.
    6. Strum grid: render strokes/beats when the song has them.
    7. Print CSS + browser print.

    Deferred to Phase 2: chord-diagram popups and transpose.

    Done when…
    • You can search, select a song, and land on its page.
    • Chords render correctly above the right words.
    • Auto-scroll works; strum grid shows when present; print looks right.
    Result / new capabilityA usable SING7: browse the library, open any song, and play along with correctly placed chords while it scrolls hands-free.

  8. Package & deploy the MVP

    GoalShip the working app as reproducible Docker containers.
    Implementation tasks
    1. Dockerfile for the Go backend; bake akordy/ into the image (COPY akordy/ /app/songs/) — Option A.
    2. Dockerfile for the Next.js frontend.
    3. docker-compose.yml with both containers, no DB.
    4. Configure ports, the backend URL for the frontend, and the song-folder path.
    5. Build and run the compose stack; smoke-test the running app.
    6. (Later) add /api/reload + Option B for song updates without a rebuild.
    Done when…
    • docker compose up brings up both containers with no database.
    • The app is reachable and serves real songs end-to-end from the baked repo.
    Result / new capabilityA reproducible, deployable SING7 MVP — the whole library and app ship as an image you can run anywhere. This is the milestone: a working app is live.

Phase 2 — enhancements (after the app works)

Real features, but the app is fully usable without them. Build them once Phase 1 is live.

  1. Chord diagrams (base dictionary + merge + renderer) PHASE 2

    GoalShow a finger-position diagram in a popup when a player taps a chord.
    Implementation tasks
    1. Backend: create a chords package with a base dictionary — common open/barre shapes (C, G, D, A, E, Am, Em, Dm, F…).
    2. Backend: merge per song — file definition wins → else base → else mark missing; tag each shape Source: "file" | "base".
    3. Backend: include the merged chordShapes in the song DTO; expose the missing-diagram list.
    4. Frontend: React SVG renderer that draws a shape from frets (-1 = muted).
    5. Frontend: popup on chord tap; show name-only when the chord has no shape.
    6. Test the merge branches; spot-check a few rendered diagrams.
    Done when…
    • Tapping a chord shows its diagram; a file voicing overrides the base shape.
    • A chord with no shape anywhere shows just the name — no crash.
    Result / new capabilityPlayers can see how to finger any chord in the song. (This is the whole reason the base dictionary exists — hence it lives here, not in the MVP core.)
    A1 confirmed, so the merge rule is final.

  2. Transpose PHASE 2

    GoalLet a player shift every chord in a song up or down by semitones.
    Implementation tasks
    1. Build a reusable transpose module: parse a name → { root, suffix, bass? } → shift root and bass mod 12 → re-spell → reattach the untouched suffix.
    2. Enharmonic policy: if meta.key is known, spell to that key’s accidentals; else default to sharps. Keep capo independent (it changes sounding pitch, not written names).
    3. Unit-test roots, accidentals, slash chords, wrap-around (B+1 → C), and both spelling policies.
    4. Frontend: a +/- control that re-renders every chord through the module.
    Done when…
    • +2 raises every chord a tone with correct spelling; suffixes (m7, sus4, add9) pass through untouched.
    • The control updates the whole song live.
    Result / new capabilityPlayers can play any song in a comfortable key.

The one thing to internalize

Prove the parser against the real 28 files before building anything else. The store, API, and even the frontend render are mechanical once the data model is right. The parser is where the format’s surprises live (bilingual labels, mid-word chord columns, the TAB block, held chords with no chord line, untagged songs) — and it’s your only guardrail, so a test harness over the corpus is your cheapest insurance.
